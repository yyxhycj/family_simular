3. 明确解释容易冲突的地方

预算只有一份。总成本 C 为全部选项成本之和；本页成本 P；其他页 O=C−P；本页容量 A=100−O；可继续投入 R=A−P=100−C。总分不足 100 也允许开局。确认页不增加费用。如果其他页已超分，A 可以为负；界面可把容量绘制为 0，但要额外说明“其他页已超出”，不能把负值清零后允许随机或开始。

初始信物三个，是可选目录数量。V5 实际允许从已解锁信物中多选，只受同一总分约束。本交付保留该行为，不重新施加“必须且只能带一件”的旧建议；是否额外限制装备/携带槽属于将来明确评审项。实体物件在局中可以继续获得，局外解锁资格与本局物件不同。

100+ 是完整内容目标。144 条旧目录是素材库，不是 144 条已开发事件链，也不承诺每个世界各 144 条。先把凡世路径做完整；正式结局发布数量单独计数。

发展条件满足不强制截断。先取得终章资格，玩家确认一个主终章，本局转只读。没有在世成员等确实不可继续情形可自动终章。跨世界迁居后仍继续本家族时叫“篇章转折”，不同时声称本局已结束。

时间不直接产生经历。世界历 156 年开局不是经营 156 年；开局祖孙三代不是玩家已经完成三代培养。本局职业人年、继任、托付、复兴证据从实际行动产生。

01 · 游戏总案与凡世王朝

1. 游戏定位与体验目标

《家业》是纯文字、多代、全员可安排的家族人生模拟器。玩家始终管理整个家族，族长只是其中一个可更换职位。每个人都具有年龄、能力、当前生活安排、亲属关系与持续经历。玩家通过安排个人、经营共同家业、处理事件与选择继任者，形成能追溯原因的家族历史。

核心感受不是“把一张资产表做大”，而是“当年由我安排的这个孩子，如今接过了家族；他做过的事又在影响下一代”。普通人也必须有价值：养家、照护、教书、保存技艺与维系关系，不只是高资质人才才值得关注。

2. 三个循环

单次操作：看清处境 → 选择人物或家族事项 → 查看可用选项、花费与条件 → 确认 → 看到实际结果和出处。不能点击后只有一个数值跳动，没有对应的人物/家史记录。

一轮年度：查看近况 → 调整主业、生活计划和共同事务 → 处理待决事件 → 推进 → 收支结算、成长与世界变化 → 重要新事件暂停。普通小事合并成摘要；关键转折保留决定权。

跨局循环：自由配点 → 经营与探索 → 完成真实信物故事 → 解锁新的开局选项 → 达成某个家族终章 → 再次在同一个总分内构造不同的家庭。局外成长主要横向增加内容，不持续扩张总分。

3. 第一世界的边界

凡世王朝暂名“大晟”，是架空古代，不照搬某一真实朝代。普通人有限寿命，无修炼、灵根、超自然延寿或祖灵直接操控。可以有信仰、传闻与未来跨世界线索，但不能让玩家靠神迹替代谋生、照护和培养。

从一户家庭起步，可发展为手艺之家、商族、书香家族、医者之家、地方望族，亦可平凡延续、分散迁居或几度重建。战争、官场、地方势力通过成员任务、资源与文字事件表现；不改造成战术战斗或地图建造游戏。时代改变不自动结束家族。

六条个人路线：耕作、手艺、商业、求学仕途、医道、军伍护卫。料理家事和休养是有效生活安排，不应只是无收益闲置。路线允许中途变更；已经学会的能力和做过的事情保留。

4. 个人玩法

4.1 能力结构

保留“潜力 / 已学本领 / 性格兴趣 / 健康”分离。当前 V5 用资质 1–5、学识/手艺/医术/经营/武艺 0–100 和体魄表达。正式版可细化，但新增指标必须实际参与行动、事件或反馈，否则不加。

资质提高成长效率，不直接赋予资格。已经积累多年的普通人可以比刚入门的高资质孩子更可靠。性格主要影响过程与关系，不频繁以随机拒绝否定玩家安排；出现抗拒时要有可见原因、持续预兆与解决办法。

4.2 主业与其他事务

每人一个主要长期安排，持续到玩家修改或出现必须重新决定的人生节点。婚事、照护意愿、信物调查、居住地属于独立状态，不因更换主业丢失。V5 的调查不占主业；正式版是否计入时间负担必须写成明确规则，不隐性减少收入。

出师只生成可选转折，不自动转行。通过应试后也由玩家选择任职、继续教书或读书。职业资格不满足时给出原因和成长方向，不能只禁用按钮。

4.3 家庭与成长

成年婚配需要双方有效且非禁止近亲；新加入者有独立身份和安排。婚配与立即生育分离；生育意愿可开关、需要满足年龄及生活规则，结果不是必然。收养形成真实亲属和监护记录，养子女成年后拥有同等可选择的族长资格。

孩子有自己的记录，不默认马上开启有费用的教育；发生启蒙机会时应提示成本并尊重既定安排。老人可以继续承担适合的工作或退休，死亡保存整段人生和关系。暂时只剩孩子时提供明确的临时照护状态，不立即结束。

5. 家族经营

5.1 公共资源

最小可运行版本包含银钱、口粮、住宅、田产、作坊、商铺、声望与已经承担的义务。任何资产描述需要对应实际效果：作坊的收入需要有人经营；地点会影响某类职业而非一律加钱；买卖、经营、赠予分别记录，避免重复收入。

5.2 目标中的个人与小家庭

后续引入个人积蓄、家庭单位与共同公库，明确工资归属、寄回金额、培养补助和债务归属。先保持一套清楚的默认分配，让不想微调的玩家能直接过年。查看明细时才展开个人收支，主界面仍看可动用资金和关键承诺。

分家/在外生活不意味着从可操作名单消失。支系既能汇总，也能进入每个人；未实现异地经营时，菜单必须写“暂未开放”，不能把不可操作 NPC 叫成可经营旁支。

5.3 关系与选择

重要援助、牺牲、失约、教育投入和传授技艺建立关联记录。某次争执要能指出起因，不靠随便抽到“反目”让昨日亲密的人突然失常。资源紧张增加矛盾可能，但不能保证产生悲剧；也要有和解、回报和普通日常。

6. 族长与代际

任意在世成年且满足明确世界规则的族人可由玩家任命，不限定性别、主支或亲生关系。主动换任不清除其他成员安排，不重置时间，旧族长继续自己的生活。

正式定位是主持共同事务与对外联系，不是全能增益装备。任职经验、人脉影响共同计划的执行，不改变他人技能事实。原型尚未有完整治理系统，不把候选标签夸大成已存在的家族自治。

同一年往返换任可以真实记事，但不增加用于结局的有效传承次数；有效交接应记录前后任、在任区间与不同身份，不能只用任数列表长度判断。暂无成年候选时用临时监护，等待成长。

7. 世界、时间与迁居

世界历、当前时代状态、本局实际年数和成员年龄分别记录。开局选项使用一条明确的时期—年份—时世映射。进入游戏后的时代变化依据世界状态；世界日历是日期，不保证下一年又被开局映射强行改回旧状态。

正式世界事件应有趋势、预警、影响范围和恢复过程。商路紧张对行商、教书、农户影响不同；不设计人人固定损失同一笔钱的“世界事件”。V5 目前为简单概率时世转换，此处是完善方向，不是现状描述。

同世界迁居要明确费用、旅程/生计影响、产业如何处理、成员是否同行、落脚后机会变化。V5 只有整族地点转换，不把它解释成完整异地支系。跨世界迁移不在首个世界交付范围。

8. 事件与叙事

三层阅读：当年摘要、重要事件正文、人物/家史详细记录。前两层保证用手机可读；第三层允许追溯。每次选择同时显示故事表达、资源支出、确定效果、概率或延迟结果；未知故事内容可以隐藏，致命规则不能隐藏。

事件至少来自人物阶段、主业、关系、资产、世界趋势、信物之一。重要选择有后续并指回原因；日常也有正向回报，不让整局只有灾难。关键调查入口要可触达、可暂缓后恢复，不依赖几十年没有保底的抽签。

基础模拟必须不依赖大模型正常运行。未来可以添加文案润色，但结构化规则和事实是唯一判定依据；生成失败用模板降级，不能让模型随便修改家产、亲缘或生死。

9. 终章

阶段成就不终局。发展终章：条件未满 → 有资格 → 玩家确认 → 结局快照 → 本局只读。不可逆终章：明确不可继续 → 自动结算。仍可翻阅成员、任职史、信物史和年鉴，不允许从只读页继续写入。

一局一个主终章，其他已经满足的方向可记在回顾中，不一次把所有主结局刷成完成。最后必须写清实际人物、时代、关键转折，不能用开局不曾拥有的“三亩薄田”套所有家庭。

10. 版本交付层次

第一层是 V5 等价重构，不变玩法不变视觉。第二层把凡世核心做到一致、可靠、可长局。第三层增加人物关系、个人财产、支系与丰富世界内容。第四层完成经验证的多路线内容，再逐个讨论其他世界，累计达到至少一百条有意义的正式结局。

每层都必须能独立游玩。不以“未来会接 AI / 加一百个事件”掩盖当前没有可运行的核心循环。

02 · 开局配点与当前数值基线

本文前半部分是冻结的行为规则；后半部分是从 V5 提取的当前参数。数字用于复现原型，不意味着已平衡。完整原始选项与描述见 data/v5-config.snapshot.json。

1. 唯一计分函数

计算由一份结构化草案驱动，不从卡片文案或 DOM 读取成本。总分 C = 时世 + 地区 + 来历 + Σ每人基础人口 + Σ资质 + Σ已有本领 + 家底 + 家风 + 外部关系 + Σ已选信物。所有入口调用同一函数：页脚、家谱、明细、随机生成、开始校验、导入草案。

用整数最小单位存储价格，例如 1 点 = 10 单位；展示层再格式化。避免卡片四舍五入后看起来 100，实际 100.01 的冲突。出现 NaN、未知选项 ID、重复信物或非整数人数均直接报错，不能按 0 分或默认最高收益计算。

分页公式见冻结决策 R09。预算不足允许保留草案及跨页调整。最后确认必须重新读取最新草案，不使用打开确认窗那一刻缓存的合法状态。没有自动平衡，也不要求把点数用尽。

6. 合法性与自由边界

只验证世界与数据能否成立，不按策划的偏好强制均衡。当前原型：至少一位成年首任族长；人物年龄0–92；配偶成年且双向对应；父母/养亲年龄差至少18；没有祖先循环、无效引用、直系或共享已知祖先的配偶关系；幼童不能携带成人专业经历；安排满足年龄与技能条件。

这些年龄和关系阈值是原型参数，正式世界需单独审校。尤其不能把“年龄差不够”错误修复为自动修改已有成员年龄；应定位到具体人，由玩家修改。

7. 随机与撤销

输入为本页容量、其他页快照、当前解锁集合和随机源。输出为只包含本页字段的候选。生成后再次计算全局成本与亲缘合法性；无解就保留原稿，解释“其他页已用尽预算”或“预算不足以生成合法候选”。不能无限重试，也不能为了返回结果动其他页。

撤销保存本页修改前快照。该页发生后续手动编辑时失效；别页修改不被撤销覆盖。用户在别页花掉了余量后撤销本页，可能恢复出超分草案，允许保留，但必须阻止开始。整局随机另有独立确认与撤销记录；不能使用“随机本页”偷偷执行全局随机。

正式版需要记录用于生成候选的 RNG 状态，便于重现与测试；这是实施建议，V5 的开局随机目前直接使用 Math.random()。

8. 平衡方法

先对当前价格建立无收益/重复收费/文案不符检查，再测试集中投资来历、人口、单个天才、资产和信物的极端组合。不预先把玩家拉回平均配置。每种集中投资至少有可解释的强项和风险；不能通过隐藏惩罚去压制用户的自由选择。

价格修改必须同时版本化、更新说明和回归原型案例。运行中的家族保存原开局快照；不可因新版本涨价就把旧家族变成非法存档。导入旧草案则提示采用旧规则保留还是新规则重算，不默默删项。

03 · 手机 UI 与逐页交互规格

1. 设计基准

以 V5 为已接受视觉，不重新提出另一套风格。墨绿为书封与主操作，米白为阅读内页，草绿表达选中/进展，赭红表达成本警告和风险。纯文字不等于所有字号一样，也不等于后台表格。界面应像可操作的家谱，但所有按钮要让第一次接触的人看得懂。

设计 token 来自 source/prototype/mobile.css：背景 #f5f3ed，卡片 #fffefa，正文 #263c33，次要文字 #616b63，弱化文字 #7b8176，分割线 #dddeda，强调色 #37634d，危险色 #a44e38。保留系统中文字体回退，不依赖外部字体请求；包中不分发字体文件。

目标正文15–16px、故事行高约1.85–1.95、输入16px、主要按钮约46–49px。最终由真机检查决定，不以小字号挤入更多字段。触控热区至少44px是本项目设计目标，不代表本包已通过任何外部认证。文本放大、不依赖颜色提示、焦点可见和减少动画为必要体验要求。

2. 导航和页面结构

创建流程：世道 → 族人 → 家底 → 信物 → 落笔。五步能回访；返回不丢草案。头部有家谱和更多菜单，底部固定预算与下一步，下一步≠立即花资源。

游戏导航：家族 / 族人 / 家业 / 藏阁 / 家史。家史包含历代族长、年鉴、终章子入口。推进年份是独立主操作，不伪装成第六个底部 tab。藏阁区分本局实际物件和跨局解锁收藏，标题必须标清范围。

层级规则

最底部导航固定；年度推进条在其上方。安全区、底部浏览器工具栏和软键盘占位均计入可用高度。内容应留出足够底部空间，最后一个选择和保存按钮不能被遮挡。长人物详情是整屏面板；短菜单、预算/家谱查看用底部面板。弹层打开时锁定背景滚动，关闭回到原焦点和原滚动位置。

“概况 / 安排 / 经历”在 V5 是同一人物详情的章节定位，并不是切换到三个互相丢状态的表单。正式版保留这个使用结果，内部可使用明确路由或组件，不再按文案正则查找按钮。

3. 页面 P01：世道与来处

上方五步、页级随机/撤销、世界标题和已选家谱入口。姓氏可编辑；时期用单列整卡，年份使用当前时期的选择控件；推导时世显示为只读结果。来历与地区显示名称、总价、实际效果和选中标记。

点击时期时联动年份/时世/预算/家谱，其他字段不动。长效果可展开，不把关键代价藏在详情。当前页分值放底栏，全球100点放预算详情。超分只出现清楚提示，不阻止玩家返回前页编辑。

4. 页面 P02：家中这些人

不使用必须横滑的表格。列表卡显示姓名、年龄、代际、主业、资质、本领摘要、当前花费、族长标记和“查看与编辑”。可添加、移除、指定首任族长。删人前说明被引用的关系和族长选择会受影响，确认后重新校验，不把无效引用带进开局。

个人编辑分基础资料、亲属、潜力与经验、初始安排。年龄输入使用数值键盘；关系选择显示名字与年龄，不能只有内部ID。保存按钮固定，错误在相关字段和顶部汇总同时可见。尚未保存时预览临时变化，取消回退。任何潜力/人数变化都实时计价。

5. 页面 P03：安身家底

现银、存粮、田地使用标签明确的步进器；给出单位、当前数量、单价与本项点数。最小值0不能减为负；输入非法数字需就地提示。住宅单选，产业独立开关；家风与关系逐项选择。每次变更同步家谱和估计收支。

把“初始拥有资产”与“后续每年收益”分开写。作坊无人经营时明示不会得到经营收益。不能因为总分超出就拒绝输入，草案仍可调；开始时统一限制。

6. 页面 P04：随身旧物

已解锁项展示名称、点数、故事入口、作用、是否带入；未解锁项显示锁定状态和线索。可以查看锁定详情，不可勾选。已选不代表无条件拥有升级版本；多选遵守总分，当前不引入额外槽位。

随机只在已解锁池产生组合。查看藏阁再返回恢复同一页草案；新解锁提示不能覆盖玩家当前填写的数据。基础物件与进阶物件保持可读区分，不以“稀有金色”暗示一律更优。

7. 页面 P05：落笔之前

展示完整家谱摘要和各页费用。错误包含具体项目和跳转入口。显示总计与上限，不重复列一个会被收费的“确认页”。开始按钮禁用的同时旁边解释原因；清空错误后恢复。正在确认覆盖旧局时，保留取消入口、说明收藏保留范围；最终提交再次校验。

整局随机与普通开始分离，需确认；撤销可见。未花完的点数不阻止开始，也不会自动兑换成家财。

8. 页面 G01：家族近况

先展示当前年份/时代/家族印记和简短近况，再显示人口、钱粮、声望及必要趋势。正文重点是待决事件或上一年结果，不是六张同等优先级的大卡片。族长、近期记事、需要注意的成员均可直接跳转。

资源显示需区分“当前余额”“今年预计变化”“已经结算变化”。推进有待处理事件时，把用户定位到事件，说明原因，不悄悄忽略。推进按钮显示忙碌状态，连点只提交一次。

9. 页面 G02：事件决定

正文→来源/涉及人物→选择执行人（适用时）→选项→结果预告→确认。选项整卡可点，选中有勾选与边框，不能只有颜色。花费不足时保留可读说明并禁用；未选择时不能确认。提交后显示实际结果和家史入口。

预计一年后发生的事情不能当作当场已得奖励。调查者离世、物件出售、其他前提改变时显示新的处理方式；不让失效事件永远堵住推进。决定提交采用事件实例ID，旧弹窗不能重复扣款。

10. 页面 G03：全体族人和详情

列表能按在世/成年/孩子/已故以及姓名筛选；空结果给清空筛选入口。所有族人都可访问，不因分页/虚拟化失去某个角色。长局只优化渲染，不改变玩家操作范围。

详情顶部姓名、角色、年龄、当前主业；概况展示能力与关系；安排展示当前选择、合法性、下一年成本；经历倒序记录。保存操作与返回分离。已故或已终局成员详情只读；婚事、生育计划、应试等按钮只在满足条件时出现或解释禁用原因。

11. 页面 G04：家业

显示公库、粮储和本年估算，附展开账目。资产卡列出数量/经营者/效果/维护费，可置办或迁居。重大支出二次确认，确认时重新检查金额与对象，不重复扣款。

个人财产、分支账目未实现时不显示假余额。后续引入时以“公库 / 各户 / 产业”清楚区分范围，不把所有钱默默合并。

12. 页面 G05：藏阁

两个范围：本局物件（实际存在、保管人、调查进度、出售状态）和已解锁目录（下局可选资格）。物件详情展示来源、历史、当前状态、托付/继续调查/出售。出售的损失明确写出；已解锁资格不因出售消失。

调查有多个阶段时显示当前步骤和可操作项，不展示保证未来成功的假进度。取得新解锁使用轻提示并入历史；不强制跳出当前事件。

13. 页面 G06：家史、继任与终章

家史子导航必须可见。年鉴按年/人物/事件来源查看；历代族长显示不同的任职区间而非只显示任数；点击可以读完整人生。继任面板能比较候选当前工作和已有经历，确认后不把候选从主业中移走。

终章分可探索、已有资格、已达成；设计条目明确标识且不能结束游戏。确认发展终章前说明本局只读；最终页显示主结局、真实年数、世代、关键人物与历史依据，可翻阅旧史或创建新局。

Asset / Household 资产id、类型、所有者范围、经营者、产出/维护、处置记录；个人与公库分开
RelicDefinition 内容id、世界适用性、价格、基础解锁、事件入口、效果条件、可变形态与解锁条件
RelicInstance instanceId、definitionId、来源、所属家族、custodianId、状态、事件阶段、托付史、出售/转化记录
EventInstance instanceId、definitionId、世界/版本、来源事实、参与者、排队/到期时间、状态、选项与实际结果
EndingRecord endingId、runId、世界、主终章时间、条件快照、关键人物、证据事件、当时内容版本 

`households`与细分关系是目标状态，V5还没有完整实现；迁移时先为既有成员建立一个默认家庭，不能凭空编造个人资产。`RelicInstance`独立编号是为了避免同种物件/不同代际混淆，V5当前大多按定义id识别。

## 3. 编辑状态与运行状态隔离

草案可以超分、可以暂时不完整；运行状态不允许非法开局。人物编辑再用一个 `editingMember` 副本。预览读取副本合成的临时草案；保存通过字段校验后替换草案，取消丢弃副本。未完成表单不能污染现有RunState，也不能写入Profile解锁。

确认开始：读取最新草案 → 全量验证 → 计算价格 → 检查内容解锁 → 有旧局则显示覆盖说明 → 用户确认 → 再次验证 → 建立开局快照与新runId → 一次保存 → 跳转家族页。任何失败保留原家族；不要先清存档再尝试创建。

## 4. 命令与只读计算

计算价格、资格、预计收支、结局进度是纯读取，不修改世界和RNG。所有写入通过明确命令处理：`CreateRun / SetAssignment / AdvanceYear / ResolveEvent / AppointLeader / Marry / Adopt / MoveFamily / TransferRelic / SellRelic / ClaimEnding / ImportSave`。

最小命令结构可用 `commandId, runId, expectedRevision, type, payload`。命令处理器先验证当前状态，再计算候选副本，写入结果、日志与相关解锁，最后替换并保存。相同 `commandId` 或已处理的事件实例重复提交，不重复扣款或推进。原型本地单机无需引入复杂远程编排，也不强制建设完整事件溯源平台。

运行结束后默认拒绝写命令。重新开局是新runId；导出和查看保持可用。自动终局也要检查自己的条件，不能内部函数只因接到 `last` 就结束仍有成员的家族。

## 5. 年度事务顺序

1. 确认本局未结束、没有阻断事件、必须交接时已处理；加推进锁。
2. 冻结年初在世成员、主业、资产、时代和价格快照。收入资格依据该快照，不把年末新生儿算全年收入。
3. 计算收入、教育学艺支出、居住生活成本、食物生产和消费；记录各分项。
4. 按明确顺序执行卖粮补现金、买粮补口粮；记录是资产转换而非重复经营收入。不足生成困境后果，不凭空把债务或差额当作已偿清。
5. 依据年初主业累积职业人年、能力和健康，再推进年龄。出师只安排决定节点。
6. 判定离世并保存人物历史；处理族长空缺、保管人回收、调查执行者失效；不删除实体物件或亲属记录。
7. 处理实际生育、合法加入者、到期后续以及世界变化，使用可保存的随机源。新加入者从其规则规定的时点开始消费，明确是否使用整年或半年的简化模型。
8. 对本次事实更新稳定年数、传承、帮助、迁居等统计；形成年度摘要及独立记事。
9. 检查不可逆终局；评估但不自动领取发展终章；保存新年度、事件、日志、RNG状态和相关解锁，统一提交。
10. 提交成功释放锁并渲染；失败恢复之前状态和RNG，不留下“扣钱了但事件没写进去”的半年度。

年度锁要防连点、重复触摸与快捷键，不仅灰掉页面按钮。加载失败不能通过重进页面产生多推进一次。预估不含突发事件时在UI直接说明。

## 6. 随机与可复现性

正式实现采用分离的开局随机、年度模拟随机、纯文案随机状态。打开人物页或重新渲染不能消耗模拟随机数。存档保存各源状态；相同输入、版本、命令序列得到相同结果，便于回归。

V5 `rnd()`用于部分年度逻辑，而本页随机使用`Math.random()`，部分初始化还引用全局草案。重构时要去掉这些隐式依赖，但先在回归中记录差异，不能一边重构一边改所有寿命与概率。

## 7. 存档与恢复

包容三种数据：Profile、Draft、Run；都要版本号。一个保存事务产生同一修订号，不分别写成不匹配的“已得到信物但未有解锁记录”。保留最近可读备份；存储失败明确告知临时状态并提供导出。

导入步骤：读取到隔离对象 → 限制文件大小 → 结构与引用校验 → 查版本 → 迁移预演 → 显示将替换/保留内容 → 用户确认 → 原子替换。未知世界、事件或旧内容缺失不能随意映射到第一个选项；应保留原存档并给出不支持原因。

现有V5使用独立localStorage键但存档schema仍沿用历史结构，不能仅看UI版本判断可读性。先为V3/V4/V5建立固定输入输出夹具。已经运行的旧家族保留真实日期、经历与资产；需要修正的是新建草案的时期年份映射，不是抹掉旧局历史。

预算涨价不反向废除已有家族。终章快照不随以后条件调整重新解释。已解锁记录与物件出售史不能被导入一个更旧草案意外覆盖，导入策略必须明示。

## 8. 轻量内容驱动

事件与结局条件使用注册的操作符与函数，不把JSON里的任意字符串直接`eval`执行。例如年龄门槛、持有物件、实际职业人年、特定选择和历史交接分别有可测试的条件函数。效果使用允许的领域操作，不直接写任意字段。

外部内容默认不能加入脚本。旧目录中的历史`engine`字段不能作为已实现证明，也不自动调用代码。条件、选项、奖励与结局登记分别有内容状态，见下一章。

## 9. 平台与性能

先确保原型在普通浏览器工作，再决定部署。正式移动网页使用稳定来源存储和可导出备份；预览壳不等同独立App，文件协议与iframe的存储隔离需要单独提示。原生封装/云同步不是当前硬前置。

长局不能靠删除族人解决性能问题。成员列表、年鉴和图鉴分页或虚拟化；已故人物保留可追溯历史。屏幕局部更新，不每次输入都重建整个世界DOM。测量实际耗时与存档体积后再优化，不预设未经测量的性能达标数字。

05 · 事件、信物与结局内容生产

1. 内容状态要可辨认

每条内容使用 idea → specified → implemented → verified → published 状态。idea只有想法；specified有条件、选项和后果；implemented能运行；verified已有达成/不可达/边界测试；published才计入正式可玩数量。若某个状态的证据不足，不能因为UI有卡片就跳级。

V5现有13条终章有判定函数，但不等于全部已经通过长局与平衡验收。历史144条目录是设计参考，混有已不适用参数、跨世界条目与旧engine标记；需逐条重新归属，不自动变成实装注册表。

2. 每条事件的策划表

必须写出：稳定ID、世界、主题、何种人生/家族状态触发、如何首次发现、是否阻断推进、参与者选择、资源和前置条件、每个选项的即时效果/延迟效果、取消与恢复、重复规则、关联信物/结局、日志模板、正反测试。

正文只讲情境，不偷偷决定人物行为。选项说明区分确定花费与可能收益。例如“花8两，一年后查到线索”，不写成“花8两必定获得高级图纸”。同一选项在前提变化后要重新校验，不能旧画面还允许给已出售物件领奖。

事件实例使用自己的ID，即使同一个模板隔十年再来，也是另一实例。重复提交同一实例无新收益；允许发生的重复日常也不能无限刷声望。

3. 家传物的三层

定义属于内容目录；解锁资格属于玩家档案；具体物件属于本局家族。托付只改具体物件的保管人，不改拥有者，也不重新给一次解锁奖励。保管人离世回收到家中，可重新交给成年成员。

出售导致保有效果停止、未完成调查取消、相关待决节点失效；既有历史与跨局资格保留。转化、遗失、捐赠应有独立状态，不都叫出售。正式版多件同类物件以实例区分，V5按定义id识别的简化需先迁移。

5. 一条信物事件链的最小闭环

以老木尺为首条纵向样本：

  1. 创建时选择已解锁木尺，扣开局点数而非公库钱；局中生成独立实例和保管人。
  2. 开篇发现匠号，显示来源并可选择成年调查者。
  3. 立即查访8两/一年，慢查4两/两年，暂缓0两；费用是V5原型参数。
  4. 提交一次决定；记录dueYear、actor、route、sourceEvent。主业保持原样。
  5. 年度推进到期才排入后续；执行者离世时按明确接手流程，不凭空复活旧人。物件出售则取消。
  6. 后续选择修复或交给当地匠人。不同选择有不同记录和状态；只有对应路线解锁营造图。
  7. 同一解锁只登记一次，与事件结果同一存档事务保存；下次开局能选，新总分仍100。
  8. 木尺相关终章读取真实查访/修复与职业/交接事实，不仅看当前收藏有图纸。

验收不仅要跑成功路径，还要跑钱不足、暂缓再继续、慢查、执行者去世、保管人换人、物件出售、连续点击和存档往返。

6. 终章定义

每条终章有：id、worldId、家族主题、性质（发展/不可逆/特殊）、所需事实、禁止条件、提示策略、确认方式、回顾模板、解锁奖励（如有）、关键证据、正向样本、差一项样本、边界样本。

禁止把开局已经有高学识等同本局培养，或把两次同年换人等同真实传承。涉及持有、托付、援助、复兴、职业继承的条件都要读取历史事实，不从最终余额猜测发生过什么。

一个新结局至少在玩家行动路径、必须承担的取舍、最终家族状态中有实质差异；只提高一个资源阈值的条目降为同一结局评价档位，不算新结局。

终章文本必须从快照生成，允许兜底句但不能编造实际没有的孩子、祖宅或功绩。隐藏结局可以隐藏名字/文案，不能隐藏导致整局终止的风险。

7. V5十三个演示终章

炊烟未断、书香传家、商脉长存、百年手艺、杏林人家、四时有余、一村归心、异乡生根、归来有灯、迟来的家书、木尺新纹、家谱再续、家谱落笔。完整条件从代码提取到 data/v5-endings-13.snapshot.json；其中有函数源码字符串用于审计，不直接当正式内容执行。

例如“百年手艺”目前只要求两代各实际手艺3年、经营中作坊和真实交接，名称并不对应100年时长。正式内容审核需确认是改名还是调整路径；不要为保住名称强迫新增空等100年条件。类似文案与规则的偏差要逐条登记。

8. 从现有目录走到上百结局

批次0：校对现有13条，逐条跑条件达成与未达成、真实历史、重复提交、只读。

批次1：凡世六条职业与普通家庭路线扩充，优先补现有系统能支持的独立路径。没有官场/分家系统的结局先留specified，不用一个虚构布尔值直接发奖。

批次2：随着外部关系、个人家庭、迁徙和支系系统实装，接入相应信物与事件链，再发布关联终章。

批次3：第二世界先单独定规则，再审查适用条目。跨世界解锁先做故事与开局关联，真正携族迁移另立完整方案。

完整游戏发布目录至少一百条经验证的独立结局；144是可复用的旧素材数量，不强制12×12分类，也不保证一世界承担全部目标。每批发布数量以“满足published状态”的清单计算。

9. 世界关联的内容字段

预留来源世界、发现事实、解锁目标世界、目标开局选项、携带何种“记录/实物/人物”、是否新runId。先明确是玩家知识、流传实物还是同一家族迁移，三者不能混写。

凡世必须独立有完整终章，不强制成为其他世界教程。后续增加关联时不能重写玩家已经结束的家史去补设定；可以新增解释和线索，但保留事实快照。

10. 模板与审查交付

本包 templates/ 有事件、信物、终章和任务验收模板，均标记为目标格式样例，V5不会自动读取。制作一条内容的顺序：策划填表 → 条件/效果审校 → 内容实现 → 正反样本 → 文案复核 → 手机展示检查 → 版本登记。任何一步缺失，不能计作正式可玩内容。

06 · 逐步实施手册

本手册用于在正式工程中实施，不表示这些开发步骤已经完成。V5提供参考行为，本交付已完成原型整理与局部冒烟。每步先完成当前目标、验证，再继续；不允许一次提示让工具重写全项目。

一、先后顺序与可试玩节点

A（S00–S01）保基线 → B（S02–S05）规则与存档 → C（S06–S10）创建闭环 → D（S11–S18）完整凡世纵向切片 → E（S19–S20）内容与家庭深度 → F（S21–S25）正式体验与发布 → G（S26）下一个世界。

07 · 测试用例与发布验收

1. 测试证据边界

TC-BUD-04　前提：其他页成本已经101。 操作：打开一个0分页面并随机。 预期：解释容量不足，其他页不变，不能开始。

TC-BUD-05　前提：数字NaN/Infinity/非法负资源。 操作：计算预算和开始。 预期：拒绝非法草案，不按零费用蒙混。

TC-BUD-06　前提：确认覆盖框已打开。 操作：草案在确认前变成超分。 预期：最终处理器重新校验，原局原样保留。

TC-BUD-07　前提：人数从2变成8。 操作：提升每人资质并查明细。 预期：每人资质逐项计分，不存在全族固定低价。

TC-BUD-08　前提：价格数据采用小数。 操作：反复加减再到100边界。 预期：同一最小单位运算；显示与闸门一致。

4. 代码观察与开发风险（不是已修复清单）

函数后置覆盖。HTML保留多代实现，后面的setupView/validateDraft/startGame/commitImport等会覆盖前面的函数。源码导航需查看最终定义和其引用的旧版本；只复制第一段会退回V3规则。

移动UI依赖旧DOM。mobile-ui.js用MutationObserver、选择器和可见文案匹配原按钮并创建移动导航。适合原型快速迭代，但改标签/结构可能失去入口，正式化应迁为稳定组件/命令绑定并用导航测试保证同等可达。

随机与纯函数。开局随机使用Math.random()，年度用独立rnd()；buildMember寿命读取全局draft.seed而不是显式参数。需要分离RNG和配置输入。当前不承诺整局回放可复现。

自动终章守卫。当前finishRun对非auto条件进行校验，auto路径依靠调用方；正式命令也应独立验证全员归零。当前UI正常流程不意味着底层所有入口安全。

经济、关系、世界为简化。多数来历与往来关系仍是固定增量；有基本地区/时代调整和整体迁居，但不包含完整个人财产、商路风险、官场、分支关系。不能从名称推断复杂系统已经实现。

内容名义与条件。“百年手艺”等名称未要求百年；某些物件故事文案暗示实体，但代码只登记下一局资格。正式化需逐条核对叙述与状态，而非只润色诗意文本。

测试局限。38个冒烟不覆盖所有UI字段、所有13终章的正常长局路径或所有导入情况。正式发布需要S22–S24。

10 · 阶段里程碑与待定事项

1. 三个真正能验收的阶段

阶段一：与V5行为相同、内部可维护。完成S00–S10并能回归现有游戏。五步、预算、时间、随机、预览、开始、导出导入和手机导航均不退化。不是让玩家等着一份重写后打不开的代码。

阶段二：首世界可靠纵向切片。完成S11–S18。一个正常合法开局能完成个人安排、年度、成长、继任、信物查访、解锁、新局和主终章闭环；分值/事件仍可有限，但不能是只读故事或用测试按钮直接发结局。

阶段三：首世界内容与发布体验。完成S19–S25。家庭/支系等深度系统按计划落地，内容逐批验证，真实手机与存档验收完毕。有明确的可玩目录、已知限制与可恢复版本。其他世界在S26单独讨论，不挤占首世界核心完成度。

2. 可由实施默认处理的细节

本包建议先继续现有HTML/JavaScript，模块化规则与视图；使用可保存随机状态、整数最小点数单位、稳定实体ID、同修订存档、显式页面绑定。这些是实现方式，允许团队在保留行为的前提下选择等效实现。不要因为框架偏好重做设计。

先保留V5可多选已解锁信物且共享预算。先保留当前世界的年龄、职业、价格作为回归数据，随后有专门平衡步骤。先采用本地单人，无需登录与云端。未选择最终平台前不承诺App安装包。
